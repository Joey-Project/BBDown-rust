# Automatic CDN routing plan

This is a design for a later, separate implementation PR; this design document does not report measurements or change current routing. The historical baseline covers two representation sizes, two short morning windows, and 18 successful downloads. Two later valid three-group runs are recorded in the [expanded live measurement journal](project_journal/2026/10/2026-10-11-cdn-expanded-live-measurement-01a12c87.md). Neither record establishes stable speedup, all-day or multi-location performance, or a global default route. Transfer activity timestamps omit connection and response-header wait, so they cannot be presented as full request latency or TTFB.

## Existing contract and opt-in boundary

- With automatic selection disabled (the default), retain today's ordered media URL behavior. `DownloadOptions::default()` has `cdn_probe = false` and `cdn_parallelism = 1`; `MediaHostOptions` has no replacement host or candidate pool. Do not silently add probes, rewrite hosts, or persist route state.
- Keep manual `upos_host`, ordered `cdn_hosts`, `cdn_preset`, `cdn_probe`, and `cdn_parallel` controls authoritative. Automatic selection is a separate explicit opt-in (`--cdn-auto` and a corresponding `DownloadOptions` builder/config field); it must not be implied by a preset, `--cdn-probe`, or parallelism. Reject or define conflicts explicitly instead of silently combining policies.
- Keep `ClientConfig` endpoint, credentials, playurl mode, and PGC route separate from media-host policy. `bbdown-core` callers opt in through download options; the CLI maps only the explicit download flag/config setting. Public playurl resolver choice and restricted-area PGC routing never become inputs to media-host ranking. Resolver/API failures belong to the resolver/API operation, not a CDN host-health record.
- Automatic mode may rewrite only the authority of a media donor URL. Preserve its scheme, signed path, query, and required media headers exactly; never log, store, or emit credentials, cookies, full URLs, paths, or query strings. Diagnostics expose a sanitized host authority and stable reason enums only.

## Candidate selection and safety

1. Build candidates from one resolved representation's primary URL, its backups, and explicitly configured media-host candidates. Do not mix qualities, stream IDs, or independently resolved playurl responses. Preserve the original donor URL as a fallback.
2. Reuse the existing `probe_media_cdns` sampling operation for Stage 1 automatic selection: allow up to 64 KiB of sampled response body per candidate and a five-second probe deadline, including unknown-size discovery. For an initial experiment, cap selection to four distinct authorities total (including the original), so the nominal aggregate sample-body budget is at most 256 KiB before in-flight/cancellation overshoot. These are explicit opt-in bounds, not measured optima. Keep this separate from the internal shard compatibility probe, which samples up to 16 KiB per candidate with its own two-second limit; it checks Range compatibility and is not the 64 KiB ranking measurement. Verify actual body bytes and cancellation overshoot in mocks before fixing aggregate budgets.
3. Reject candidates unless they pass exact HTTP 206, requested `Content-Range`, total-size, declared `Content-Length` when present, and actual body-length checks. Candidate grouping may also require equal scheme, path/query, total size, and sampled bytes. A matching sample and size mean *compatible for this attempt*, not identical full-file content. Never combine different representations on this evidence alone.
4. Stage 1 has no host-health state. Among candidates whose full `probe_media_cdns` sample succeeded and passed its response/range/length validation, sort by measured sample throughput descending, then that probe operation's elapsed time ascending, then configured candidate order for a deterministic tie-break. The throughput uses the sampled body bytes divided by the elapsed time for that complete sampling operation. Failed or unmeasured candidates do not enter the ranking; if there is no usable measurement, retain the ordinary ordered/original fallback. This sample ranking is a proposal for later opt-in validation, not a global best-host claim. Transfer activity events omit request-start and response-header wait, so they are not full latency/TTFB; do not derive ranking latency from activity spans or add spans across concurrent hosts.
5. Keep one-host parallel ranges valid: if only one candidate is compatible, all lanes may use that host, matching current behavior. Do not require host diversity for a successful sharded transfer.
6. A failed range may retry the exact same byte interval on another compatible candidate. Stage all bytes in temporary storage and publish only after every interval validates. If the sharded attempt has an ordinary recoverable error, use the existing whole-file path and report the reason. Cancellation is terminal: propagate it without starting a whole-file fallback or another route attempt. Destination validation and atomic publication remain mandatory.

Signed URLs need special care: preserving a signed path/query does not prove that another authority accepts the signature, maps the same object, or serves a stable representation. A candidate-specific transport, HTTP, or range mismatch excludes that candidate for this attempt. An expired/invalid signature or other response that could apply to the whole signed representation must not poison every host globally; retain the normal download error/fallback behavior and attribute resolver/playurl errors to that operation. Do not refresh credentials or invoke another resolver as a side effect of CDN selection.

## Host-health state

- When Stage 2 adds host health, start with process-memory state only. Key by normalized scheme, host, and effective port; never key by URL, path, query, media ID, user ID, credential, or cookie. Store only bounded counters/outcomes and probe elapsed/throughput summaries needed for ranking. Do not persist sampled media bytes.
- Proposed Stage 2 experimental bounds: at most 64 host records, a 15-minute TTL, and a small bounded recent sample (for example, the latest 8 outcomes per host). Expire records on TTL. A successful probe clears that host's failure penalty and adds or refreshes its successful measurement; it does not delete the host record. Clear all state on opt-out, cache-version change, or explicit reset. Do not cache credentials or signed URL validity. A process restart naturally clears the first implementation's state.
- If later evidence justifies disk persistence, make it a separate opt-in with a versioned host-only cache under the application's cache directory, restrictive permissions, atomic replacement, entry/size limits, and the same TTL. A missing, malformed, unreadable, or old cache falls back to the current ordered route and is never a download failure. Do not introduce persistent state in the first routing PR without a demonstrated need.
- Count only host-attributable probe/transfer outcomes. Do not mark all candidates unhealthy for playurl/API resolution failure, missing credentials, cancellation, local disk errors, destination rejection, or an ambiguous signed-URL expiration. Distinguish unknown/unreadable state from an expired record.

Live runs remain explicitly opt-in. This is a proposal for later, separate PR review; the design itself reports no measurements. ## Interface and diagnostic follow-up

The current interfaces already provide `MediaHostOptions`, `DownloadOptions::with_cdn_probe`, `with_cdn_parallelism`, `probe_media_cdns`, Range diagnostics, and CLI host/preset/probe/concurrency flags. A later PR should add a distinct opt-in policy without changing the meaning of those controls. Extend diagnostics only with sanitized host, phase, bounded outcome, and measured operation duration as needed. Add request-start plus response-header timing before publishing full request latency/TTFB; `transfer_activity_by_host_phase` remains body/diagnostic activity only. Keep consumed decoded body bytes distinct from wire bytes, and keep `RequestFinished.bytes_received` as a final watermark rather than an increment.
