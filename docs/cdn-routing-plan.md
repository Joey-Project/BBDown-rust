# Automatic CDN routing plan

This is a design for a later, separate implementation PR; this design document does not report measurements or change current routing. The historical baseline covers two representation sizes, two short morning windows, and 18 successful downloads. Two later valid three-group runs are recorded in the [expanded live measurement journal](project_journal/2026/10/2026-10-11-cdn-expanded-live-measurement-01a12c87.md). Neither record establishes stable speedup, all-day or multi-location performance, or a global default route. Transfer activity timestamps omit connection and response-header wait, so they cannot be presented as full request latency or TTFB.

## Existing contract and opt-in boundary

- With the proposed automatic policy disabled (the default), retain today's ordered media URL behavior. `DownloadOptions::default()` has `cdn_probe = false` and `cdn_parallelism = 1`; `MediaHostOptions` has no replacement host or configured candidate pool. Do not silently add probes, rewrite hosts, or persist route state.
- Existing `--cdn-probe` and `--cdn-parallel N` already trigger the downloader's automatic candidate probe on the fresh-target path. In `should_probe_media_candidates`, the trigger is `cdn_probe || cdn_parallelism > 1`, except for non-regular targets and resume-enabled nonempty targets. Media streams and FLV segments use this path. `probe_media_candidates_with_progress` probes up to eight URLs from the existing primary/backup/configured donor list, validates Range responses, groups successful samples by total size and matching prefix, promotes the largest matching sample group in descending measured-throughput order, and leaves failed or other URLs in original order as fallback. If no candidate has a usable measurement, it preserves the original URL order and expected size. Thus `--cdn-probe` already reorders a compatible measured group, and `--cdn-parallel` triggers that same ordering before its separate sharded-transfer attempt.
- `--cdn-auto` is a proposed, separate opt-in policy layer, not a replacement or reinterpretation of those flags. It must leave their existing triggers and fallback behavior intact. In auto mode, construct and cap the final candidate URL list before entering the existing single automatic-probe pass; legacy `--cdn-probe` / `--cdn-parallel` and auto must share that one pass and its ranking, never probe the same auto list twice. If neither legacy flag triggers it, auto triggers that same pass once. With auto disabled, legacy flags keep their exact current candidate list and behavior. The later shard compatibility probe remains a separate operation required by sharded transfer.
- Fix manual-control composition: `--upos-host` is a hard single-host override and conflicts with `--cdn-auto` (reject the combination); auto must never silently override a manual host setting. An explicit `--cdn-host` list or `--cdn-preset` is the allowed candidate pool; auto may rank only within candidates emitted by the existing eligibility pipeline for that pool, with configured order as deterministic tie-break and fallback. With no user pool, the opt-in policy uses the bundled overseas media-candidate set through that same pipeline; it does not infer location or invent hosts. Preserve the existing CLI conflict between `--cdn-host` and `--cdn-preset`. Preserve `MediaHostOptions` defaults: core callers allow PCDN by default, while the CLI starts from `bbdown_cli_default()` with PCDN disallowed unless `--allow-pcdn` is set. Honor `force_replace_host` and the exact caller-provided `allow_pcdn` value.
- Keep `ClientConfig` endpoint, credentials, playurl mode, and PGC route separate from media-host policy. `bbdown-core` callers opt in through download options; the CLI maps only the explicit download flag/config setting. Public playurl resolver choice and restricted-area PGC routing never become inputs to media-host ranking. Resolver/API failures belong to the resolver/API operation, not a CDN host-health record.
- Automatic mode may rewrite only the authority of a media donor URL. Preserve its scheme, signed path, query, and required media headers exactly; never log, store, or emit credentials, cookies, full URLs, paths, or query strings. Diagnostics expose a sanitized host authority and stable reason enums only.

## Candidate selection and safety

1. Validate user-provided settings through the existing CLI/core validation path first; invalid manual `--cdn-host` or other host configuration retains its current error behavior and must not be silently skipped by auto. Build the future auto list from the existing `candidate_urls(primary, backups, MediaHostOptions)` pipeline, preserving the caller's options and adding only the selected explicit/bundled pool. This keeps `upos_host` replacement, ordered `cdn_hosts` and `original_after_cdn_hosts`, `force_replace_host`, and `allow_pcdn` semantics; CLI auto keeps PCDN disabled unless `--allow-pcdn` is explicit. Never reconstruct candidates from raw playurl fields or reintroduce a raw primary filtered by the pipeline. The effective donor is the first eligible URL emitted by the existing primary-source donor branch after rewrite and eligibility filtering. The allowed set contains only this donor if emitted and candidates the pipeline emitted for the selected pool. Select at most four URLs total, exactly one per normalized authority `(scheme, host, effective port)`. Reserve the effective donor first only if it is in that emitted allowed set. Then walk pool authorities in configured/bundled order; skip duplicates and entries excluded or absent from eligible pipeline output, and take the first three remaining. For each selected pool authority, prefer the first eligible resolved backup URL at that authority in backup order when the pipeline emitted it; otherwise use the first pipeline-generated pool rewrite. Backups outside the selected pool are never selected and cannot extend the allowed set or create a fifth URL. Stop after three pool authorities; overflow is deterministically ignored. If no eligible donor or pool candidate is emitted, retain the ordinary candidate list and current fallback/error behavior; do not synthesize candidates. Do not mix qualities, stream IDs, or independently resolved playurl responses. With auto disabled, keep the existing full primary/backup/manual candidate construction unchanged.
2. Stage 1 is a proposal for a future PR. Reuse the downloader's existing automatic candidate-sampling pass, not the separate public `probe_media_cdns` command/API and not a second measurement pass. That pass probes up to eight existing candidates and reads up to 64 KiB per candidate; its current per-request timeout is two seconds (with a one-second body-idle timeout). The proposed auto layer may set a five-second overall candidate-measurement ceiling, but reuse of an existing result must not extend or repeat its requests. Cap auto at four candidate URLs, one per emitted authority, including the effective donor; the nominal sample-body budget is therefore at most 256 KiB before in-flight/cancellation overshoot. The live benchmark's donor-size setup probe has a separate 64 KiB / five-second limit. Keep the internal shard compatibility probe distinct: it samples up to 16 KiB per candidate with its own two-second cap to check range-source compatibility, not throughput. Verify actual body bytes and cancellation overshoot in mocks before fixing aggregate budgets.
3. Reject candidates unless they pass exact HTTP 206, requested `Content-Range`, total-size, declared `Content-Length` when present, and actual body-length checks. Candidate grouping may also require equal scheme, path/query, total size, and sampled bytes. A matching sample and size mean *compatible for this attempt*, not identical full-file content. Never combine different representations on this evidence alone.
4. Existing pre-download ordering is already a measured sample sort: successful probes with the same total size and prefix as the largest matching sample group are ordered by sampled bytes divided by the complete candidate-probe elapsed time, descending; ties retain their input order. The proposed Stage 1 adds the bounded opt-in candidate-pool policy described above; it does not duplicate this throughput sort or measurement. Auto forms its final candidate list before the one existing pass, then uses that pass's ranked result; failures and incompatible samples remain in original fallback order. Transfer activity events omit request-start and response-header wait, so they are not full latency/TTFB; do not derive ranking latency from activity spans or add spans across concurrent hosts.
5. Keep one-host parallel ranges valid: if only one candidate is compatible, all lanes may use that host, matching current behavior. Do not require host diversity for a successful sharded transfer. The current automatic probe can still run with one URL when legacy flags trigger it, but sorting one authority has no routing effect. The future auto layer does not add a rewrite or ranking when its bounded list has only the donor authority.
6. A failed range may retry the exact same byte interval on another compatible candidate. Stage all bytes in temporary storage and publish only after every interval validates. If the sharded attempt has an ordinary recoverable error, use the existing whole-file path and report the reason. Cancellation is terminal: propagate it without starting a whole-file fallback or another route attempt. Destination validation and atomic publication remain mandatory.

Signed URLs need special care: preserving a signed path/query does not prove that another authority accepts the signature, maps the same object, or serves a stable representation. A candidate-specific transport, HTTP, or range mismatch excludes that candidate for this attempt. An expired/invalid signature or other response that could apply to the whole signed representation must not poison every host globally; retain the normal download error/fallback behavior and attribute resolver/playurl errors to that operation. Do not refresh credentials or invoke another resolver as a side effect of CDN selection.

## Host-health state

- When Stage 2 adds host health, start with process-memory state only. Key by normalized scheme, host, and effective port; never key by URL, path, query, media ID, user ID, credential, or cookie. Store only bounded counters/outcomes and probe elapsed/throughput summaries needed for ranking. Do not persist sampled media bytes.
- Proposed Stage 2 experimental bounds: at most 64 host records, a 15-minute TTL, and a small bounded recent sample (for example, the latest 8 outcomes per host). Expire records on TTL. A successful probe clears that host's failure penalty and adds or refreshes its successful measurement; it does not delete the host record. Clear all state on opt-out, cache-version change, or explicit reset. Do not cache credentials or signed URL validity. A process restart naturally clears the first implementation's state.
- If later evidence justifies disk persistence, make it a separate opt-in with a versioned host-only cache under the application's cache directory, restrictive permissions, atomic replacement, entry/size limits, and the same TTL. A missing, malformed, unreadable, or old cache falls back to the current ordered route and is never a download failure. Do not introduce persistent state in the first routing PR without a demonstrated need.
- Count only host-attributable probe/transfer outcomes. Do not mark all candidates unhealthy for playurl/API resolution failure, missing credentials, cancellation, local disk errors, destination rejection, or an ambiguous signed-URL expiration. Distinguish unknown/unreadable state from an expired record.

Live runs remain explicitly opt-in. This is a proposal for later, separate PR review; the design itself reports no measurements. See the [expanded live measurement journal](project_journal/2026/10/2026-10-11-cdn-expanded-live-measurement-01a12c87.md) for project results. Any proposed values above are testable starting bounds only; update them from measured evidence. Keep public resolver and PGC route experiments separate from this media transfer matrix.

## Interface and diagnostic follow-up

The current interfaces already provide `MediaHostOptions`, `DownloadOptions::with_cdn_probe`, `with_cdn_parallelism`, the internal `probe_media_candidates_with_progress` ordering pass, `probe_media_cdns`, Range diagnostics, and CLI host/preset/probe/concurrency flags. A later PR should add the distinct opt-in candidate-pool layer without changing the meaning of existing controls. Extend diagnostics only with sanitized host, phase, bounded outcome, and measured operation duration as needed. Add request-start plus response-header timing before publishing full request latency/TTFB; `transfer_activity_by_host_phase` remains body/diagnostic activity only. Keep consumed decoded body bytes distinct from wire bytes, and keep `RequestFinished.bytes_received` as a final watermark rather than an increment.
