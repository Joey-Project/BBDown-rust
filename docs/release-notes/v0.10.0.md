# v0.10.0 Source Preparation Notes

This document records the `0.10.0` source-preparation state on 2026-10-14; it is not a publication
announcement. At that preparation date, `0.9.0` was the latest published release. See the
[official GitHub Releases](https://github.com/Joey-Project/BBDown-rust/releases) page for current
publication status.

## Highlights

- Add `related:<video>` input for a single video's related recommendations. It accepts a numeric
  aid, an `av` or `BV` ID, or an official desktop or mobile ordinary-video URL. Embedders can call
  the typed `BiliClient::resolve_related_recommendations(aid, Option<Selection>)` API.
- Preserve the endpoint's response order, filter the seed video and entries with invalid aid or
  cid or known OGV type, and deduplicate recommendations by aid. Selection applies to the retained
  recommendation positions: `Latest` chooses the first retained item, while page and index
  selectors choose their corresponding positions. No selector or `All` returns all retained
  items, including an empty result. `Current` and `Episode` are rejected before the request.
- Resolve recommendations with one request and one response batch. This feature does not paginate
  or recursively traverse recommendation results. Authentication uses only optional
  caller-provided credentials. For example, set the `credentials` field of `ClientConfig` to
  `Credentials::default().with_cookie(...)`. Anonymous requests may encounter risk control, and the
  feature adds no credential discovery or risk-control bypass.
- Add `BiliClient::resolve_metadata_page` for `Input::FollowingFeed` and
  `Input::SpaceDynamic(mid)`. It returns a bounded metadata window under separate per-call item,
  source-record, and API-request budgets. Defaults are 100 returned items, 100 source records, and
  10 requests; hard maxima are 4096, 4096, and 512. Request accounting includes device-cookie
  initialization, WBI nav, feed, and video-view calls. Its opaque, cloneable in-memory cursor is
  bound to the input, API endpoint, and cookie context. Existing full `resolve`/`resolve_input`
  and CLI information queries keep their collection semantics.
- For authenticated `SpaceDynamic` requests, initialize missing or empty `buvid3`/`buvid4` values
  from the API's SPI endpoint in memory, preserve configured non-empty values, and cache validated
  server values across client clones. The temporary request header is updated; credentials and the
  credential store are not. This applies to the bounded metadata API and existing full resolver.
  A real-core metadata-plus-continuation check used five API requests and returned two video
  metadata items.
- Add a bounded CDN transfer comparison harness with three groups: fixed-host sequential transfer,
  fixed-host four-way Range transfer, and multi-host four-way Range transfer. Deterministic local
  CDN regression tests run in CI. The live benchmark remains ignored
  unless explicitly opted into.
- Expand the opt-in harness with downward-only run-budget overrides and optional quality/codec
  selectors that must uniquely identify a representation. Two anonymous invocations produced six
  valid downloads across the three groups; sequential transfer was faster than both Range groups in
  each invocation, and all three output sizes and SHA-256 hashes matched within each invocation.
  The [routing plan](https://github.com/Joey-Project/BBDown-rust/blob/master/docs/cdn-routing-plan.md)
  remains a proposal for separate future work.

## CDN Measurement Semantics

The comparison reports `transfer_bytes_by_host_phase` and
`transfer_total_consumed_body_bytes`: application-consumed, transparently decoded response-body
bytes by host and request phase, plus a group total. These values come from
`TransferBytesReceived.bytes_delta`; `RequestFinished.bytes_received` is a final watermark and must
not be counted again. `CdnShardCompleted.bytes` separately describes published shards. The byte
counts exclude headers, transport framing, and other wire traffic.

Each group uses a fresh output directory and one ordinary download attempt without resume or mux;
Range retries and whole-file fallback remain visible within that attempt. The live harness bounds
representations to 256 MiB, repetitions to three, candidate hosts to four, per-request timeouts to
300 seconds, and the setup and repetition deadline to 45 minutes. A needed donor size probe is
limited to 64 KiB and five seconds. Run-wide budgets are 3 GiB of consumed response-body bytes and
16,384 observed request IDs. Crossing chunks and in-flight reads can overshoot the body budget, so
it is not a wire-byte cap.

Equal output size and SHA-256 establish equality of the completed sample outputs. Matching size or
sampled prefixes alone do not establish whole-representation identity across hosts. The earlier
baseline covered two representation sizes in two short morning windows and 18 successful
downloads. The expanded run adds a short evening window with two invocations and six valid group
downloads. Sequential transfer was faster than both Range groups in those two observed
invocations; this remains a limited baseline, not evidence of stable speedup or a basis for default
tuning.

## Limits

- The CDN baseline changes no production CDN API or routing behavior. Production shard chunks remain
  fixed at 1 MiB.
- The proposed `--cdn-auto` routing layer, persistent host-health state, and adaptive chunk or
  concurrency tuning are not implemented. Existing `--cdn-probe` and `--cdn-parallel` behavior
  remains as documented; see the
  [routing proposal](https://github.com/Joey-Project/BBDown-rust/blob/master/docs/cdn-routing-plan.md).
- A consumer reported HTTP 412 for an initial `SpaceDynamic` request on a pinned `0.9.0` build.
  The new in-memory device-cookie initialization and bounded metadata flow passed a separate
  real-core check. The prior consumer V2 attempt failed before producing candidates; there is no
  successful post-fix consumer V2 or focused-smoke acceptance evidence. Long download, HLS, and
  native playback checks have not started.
  The real-core result does not establish consumer V2 or playback acceptance. See the
  [follow-up record](https://github.com/Joey-Project/BBDown-rust/blob/master/docs/project_journal/2026/10/2026-10-11-space-dynamic-request-and-bounded-metadata-followup.md).

for usage and measurement details.
