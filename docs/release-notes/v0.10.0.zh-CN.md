# v0.10.0 源码准备说明

本文描述当前 `0.10.0` 源码线，不代表版本已发布。当前最新已发布版本仍为 `0.9.0`。

## 重点

- 新增单视频相关推荐输入 `related:<video>`，支持数字 aid、`av` 或 `BV` ID，以及 Bilibili
  官方桌面端或移动端普通视频 URL。嵌入方可调用类型化 API
  `BiliClient::resolve_related_recommendations(aid, Option<Selection>)`。
- 保留接口返回顺序；过滤种子视频、aid 或 cid 无效的条目及已知 OGV 条目，并按 aid 去重。
  Selection 作用于过滤后的推荐位置：`Latest` 选择保留结果中的第一项，page 和 index selector
  按对应位置选择；未提供 selector 或使用 `All` 时返回全部保留项，包括空结果。`Current` 和
  `Episode` 会在发起请求前被拒绝。
- 相关推荐通过单次请求获取单批结果；此功能不会分页，也不会递归遍历推荐结果。认证只使用调用方
  可选提供的 `WebCookie`；匿名请求可能遇到风控，功能不会发现凭据或绕过风控。
- 新增 `BiliClient::resolve_metadata_page`，仅支持 `Input::FollowingFeed` 和
  `Input::SpaceDynamic(mid)`，按独立的单次调用条目、来源记录和 API 请求预算返回有界 metadata
  窗口。默认分别为 100 个返回条目、100 条来源记录和 10 次请求；硬上限分别为 4096、4096 和
  512。请求计数包含设备 Cookie 初始化、WBI nav、feed 和视频详情请求。返回的 opaque、可克隆内存
  cursor 绑定输入、API endpoint 和 Cookie 上下文。现有完整 `resolve`/`resolve_input` 与 CLI 信息查询
  保持原有 collection 语义。
- 已认证的 `SpaceDynamic` 请求若缺少或包含空的 `buvid3`/`buvid4`，会通过 API 的 SPI endpoint 在内存
  中初始化；保留已配置的非空值，并在 client clones 间缓存已校验的服务端值。只修改临时请求 header，
  不修改 credentials 或 credential store。此流程也用于现有完整 resolver。一次真实 core metadata 加
  continuation 检查使用了 5 次 API 请求并返回 2 个视频 metadata 条目。
- 新增有明确限额的 CDN 传输对比 harness，包含三组：固定 host 顺序传输、固定 host 四路 Range
  传输、多 host 四路 Range 传输。确定性的本地 CDN 回归测试随 CI 运行；live
  benchmark 仍处于 ignored 状态，只有明确选择时才运行。
- opt-in harness 增加了只允许调低的运行预算覆盖，以及必须唯一匹配表示的可选 quality/codec selector。
  两次匿名 invocation 共完成三组中的 6 个有效下载；两次观察中顺序传输的耗时都低于两组 Range 传输，
  且每次 invocation 内三组输出的大小和 SHA-256 均相同。
  [双语 routing plan](../cdn-routing-plan.zh-CN.md) 仍是供后续独立工作评审的提案。

## CDN 测量语义

对比通过 `transfer_bytes_by_host_phase` 和 `transfer_total_consumed_body_bytes`，按 host 和请求阶段报告
应用实际消费、经透明解码的响应正文字节数，并报告每组总量。这些数值来自
`TransferBytesReceived.bytes_delta`；`RequestFinished.bytes_received` 是最终累计水位，不应再次计入。
`CdnShardCompleted.bytes` 单独表示已发布分片大小。字节计数不包括 headers、传输封装或其他线路流量。

每组使用新的输出目录，并执行一次普通下载尝试，不续传也不复用 mux；Range 重试和整文件回退仍会记录在
该次尝试中。live harness 将单个表示限制为 256 MiB、重复次数限制为 3、候选 host 数限制为 4、单个请求
超时限制为 300 秒，并将准备与重复测试的总时限限制为 45 分钟。需要 donor 大小探测时，响应上限为
64 KiB、时限为 5 秒。整次运行还限制为 3 GiB 已消费响应正文字节和 16,384 个可观测请求 ID。预算边界
处跨界的分片和正在进行的读取可能造成超额，因此这不是线路字节上限。

完成样本输出的大小和 SHA-256 相同，可证明这些已完成样本输出相同。仅大小或采样前缀相同，不能证明不同
host 上的完整表示相同。此前基线覆盖两个表示大小、两个较短的上午时段和 18 次成功下载；扩展测试增加了
一个较短的晚间时段、两次 invocation 和 6 个有效组下载。在这两次观察中，顺序传输都快于两组 Range 传输；
这仍是有限基线，不能证明稳定提速或支持调整默认值。

## 限制

- CDN 基线不改变生产 CDN API 或路由行为。生产分片仍固定为 1 MiB。
- 提议中的 `--cdn-auto` routing 层、持久 host 健康状态和自适应分片大小/并发度尚未实现；现有
  `--cdn-probe` 与 `--cdn-parallel` 行为保持文档所述。详见[routing 提案](../cdn-routing-plan.zh-CN.md)。
- 消费者曾报告固定使用的 `0.9.0` 在首次 `SpaceDynamic` 请求上收到 HTTP 412。新的内存设备 Cookie 初始化和
  有界 metadata 流程通过了单独的真实 core 检查。此前消费者的 V2 请求在生成候选前失败；尚无修复后的
  consumer V2 或 focused smoke 成功验收证据，长时下载、HLS 和原生播放检查尚未开始。真实 core 结果不能证明 consumer V2 或播放验收
  通过。详见[后续记录](../project_journal/2026/10/2026-10-11-dynamic-request-and-bounded-metadata.md)。

用法和测量细节见[用户指南](../user-guide.zh-CN.md)、[嵌入指南](../embedding.zh-CN.md)和
[CDN benchmark 指南](../cdn-benchmark.zh-CN.md)。
