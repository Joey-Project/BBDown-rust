# v0.8.0 Source-Line Notes

The `0.8.0` source line adds an opt-in preserving danmaku refresh for existing archive entries.
The default `legacy` update policy remains compatible with the existing append-XML and ASS
regeneration behavior.

The `0.8.0` source line also adds `BiliClient::credential_account_identity` for explicit
account-identity checks by embedding servers.
It probes a selected Web cookie through the official Web route, or a generic access key /
TV access key through signed OAuth identity routes, and returns a verified positive UID
plus available username and issuer metadata. Logged-out, missing, malformed, or rejected
identity responses are errors; a health check is not identity proof. OAuth probes do not
forward the Web cookie, and diagnostics omit credentials and account IDs. The caller
retains responsibility for same-account policy and credential storage. Legacy generic-key
issuer fallback is limited to documented rejection codes within one request-timeout budget.

## Highlights

- Add `bbdown danmaku update --update-policy preserve` and the public
  `DanmakuUpdatePolicy::Preserve` option.
- Preserve existing XML structure and bytes, including unknown elements, attributes, comments,
  text, and duplicate comments. Positive decimal comment IDs take priority for deduplication;
  comments without a valid positive ID fall back to the complete `p` value and decoded text.
- Rebuild generated ASS sidecars from the complete merged XML and report `generated_events`
  separately from appended XML comment counts. When no XML baseline exists, fetched XML initializes
  the generated files; an existing ASS-only history is not backfilled.
- Stage sidecars and the updated archive together. The embedding API exposes immutable expected
  contents and staged outputs before publication, and validates content and destination again when
  publishing. Detected errors attempt rollback and report retained recovery locations when needed.

## Limits

Content validation does not coordinate external writers. Applications using File Provider or
another synchronized filesystem must coordinate materialization and concurrent writes themselves.
Rollback handles detected failures but does not promise crash or power-loss atomicity across files.
The preserving policy is opt-in; existing scripts keep the default legacy behavior and report JSON
shape.

[architecture guide](../architecture/rust-rewrite.md) for CLI and API details.
